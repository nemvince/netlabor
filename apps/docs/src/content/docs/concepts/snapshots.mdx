Snapshots and archives answer different questions. A snapshot is a point-in-time restore bundle for
one project. An export is a portable `netlabor.project/1` archive. A duplicate is a new project
cloned from an existing one.

## Restore points and their jobs

The snapshots dialog lists the same rows the API returns: name, description, creation stamp, size,
and a sha256 prefix. Below it, the job list reports progress and the terminal state of the work that
produced or consumed a bundle. The fixture below mixes three restore points with four jobs: a
completed snapshot, a running restore, a failed export, and a cancelled import.

A job's state is not a snapshot's state: the snapshot row exists as soon as the bundle is written,
while the `snapshot.create` job keeps running until every node is restarted. A failed export leaves
the snapshot rows untouched; a cancelled import leaves no rows at all.

## Snapshots

`snapshots.create` takes a project id, a name, and an optional description and returns a `JobRow`.
The job:

1. collects the project manifest (nodes, links, drawings, markers, faults, templates, files);
2. stops running nodes and records which ones were running;
3. tars each compute's node directory through the agent;
4. writes a gzip bundle plus `manifest.json`, records the sha256 and size, publishes
   `snapshot.created`, and restarts the nodes that were running.

A snapshot captures configuration and files, not guest RAM. Restoring rebuilds the project from the
bundle and its per-compute archives; it is not a VM memory snapshot.

`snapshots.list` shows the bundle metadata; `snapshots.download` returns a download URL;
`snapshots.restore` runs a `snapshot.restore` job; `snapshots.delete` removes the row and its file.
Snapshot privileges are `snapshot.read` and `snapshot.write`.

## Project export

`projects.export` streams a `netlabor.project/1` archive for one project. It requires
`project.export`. The archive carries the topology and project files; large blobs are referenced or
copied according to the export implementation, not silently dropped.

## Import and duplicate

`projects.import` accepts an archive and returns a job; `projects.duplicate` clones an existing
project and returns a job. Both run asynchronously so a large lab does not hold an HTTP request
open. Import is a replacement operation inside the new project — it does not merge into an existing
topology.

<div class="docs-callout" data-tone="warn">
  <span class="docs-callout__label">Stop before you snapshot</span>
  <p>
    The snapshot job stops running nodes to get a consistent file set, then restarts them. On a
    large lab this is visible as a short outage; take snapshots between exercises.
  </p>
</div>

## Choosing

| Need                                  | Use                         |
| ------------------------------------- | --------------------------- |
| Roll back a lab after a class         | `snapshots.create`          |
| Move a lab to another installation    | `projects.export` + import  |
| Start a variation without touching it | `projects.duplicate`        |
| Keep a topology as a reusable project | `projects.templates.create` |
